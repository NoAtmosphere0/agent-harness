Summary

Implemented and documented with Claude Code from a design spec I wrote; architecture, safety design and trade-off decisions are my own.

Approach. A hand-written loop between an LLM and three mock tools (knowledge-base search, service status, incident creation). A run is persisted and advanced one step at a time; it stops at a final answer or a limit, and pauses whenever the model wants to create an incident, until a human approves or rejects that exact call. Every decision is recorded as a trace event. The harness is reachable through a REST API and a CLI, and runs without an API key using a scripted model.

Five design decisions.

  1. Re-entrant loop over persisted state. advance() reads the run, works until it finishes or needs a decision, saves and returns; a later call resumes it. Waiting for a human is a normal return, not a blocked coroutine (§2).
  2. Approval gate in code, scoped to one call. Dispatch never runs an approval-gated tool; it parks the run on an approval that stores the validated arguments, and exactly those arguments run after approval. A rejected call is refused if proposed again (§6).
  3. Retry only transient failures, in one place each. Tool calls retry in the executor, LLM calls in the loop, both with capped exponential backoff and full jitter; the SDK does not retry (§5).
  4. Idempotent side effect. create_incident runs with a harness-generated key the model never sees; a retry after a post-commit timeout returns the original incident (§5).
  5. Errors are context; execution is bounded. Tool failures reach the model as structured observations; limits on steps, active time, repeated calls and consecutive errors end runs that do not converge, and time spent waiting for approval is not counted (§3, §6).

How to run. make install, then make demo (scripted scenario, you approve the incident) or make serve for the API with docs/postman_collection.json. make check runs lint, types and 254 tests. A real model is any OpenAI-compatible endpoint, e.g. Ollama with qwen2.5:7b (§12).

Live run. With qwen2.5:7b on Ollama, 2 of 5 scenarios followed the expected tool sequence; the others drifted off task, and one final answer claimed an incident that was never created. The harness handled every run correctly, and no incident was created without an approval (§8.2, §11.1).

Main limitations. Single process with SQLite; a tick is not atomic across a crash and there is no resume-after-crash; approvals do not expire and approvers are not authenticated; cancellation is cooperative; one tool call per step; final answers are not checked against the trace; the prompt-injection defence is basic, with the approval gate limiting the consequence (§13).

1. Overview and goals

A user gives an objective (for example “customers report failed checkouts; investigate and open an incident if warranted”). The harness runs a hand-written loop between an LLM and three mock tools until the model gives a final answer or a stopping condition is reached. Every step is persisted, every decision point is traced, and the one side-effecting tool, create_incident, only runs after a human approves the exact call.

2.1 Components and responsibilities

The REST API and the CLI are thin: they validate input and call two services. RunService creates runs, advances them one at a time per run (a per-run asyncio.Lock), runs them in background tasks, cancels them, and fails runs that are still in flight when the process shuts down. ApprovalService records a human decision and schedules the run to resume. Both the API and the CLI use the same services, so an approval behaves the same wherever it is made.

AgentLoop in core/loop.py is the whole agent loop (about 630 lines). It delegates three small pure pieces: parser (what did the model ask for), guardrails (may the run continue) and observations (what the model sees after a tool call). Tools sit behind a registry and an executor that owns timeouts, retries and output validation. The repository returns pydantic records and opens one short transaction per call, so no database session is held across an LLM or tool call. wiring.py is the composition root: the one place that turns settings into this object graph, for the API, the CLI and the tests.

2.2 Why a re-entrant loop over persisted state (P2)

A run has to stop and wait for a human, possibly for hours, and continue when the decision arrives in a different HTTP request. There are two ways to do that. The loop can stay suspended in memory, awaiting a future that the decision resolves. Or the loop can be re-entrant: each call reads the run from the database, works until the run finishes or needs a decision, saves, and returns. The harness does the second [R5].

  • Pausing is a normal return. Repository.pause_for_approval writes the approval, the run's pending_tool_call and the WAITING_APPROVAL status in one transaction, so a decision can never find a pending approval on a run that is not yet waiting for it.
  • Resuming is any later advance() whose run has a decided approval (_ready_to_advance). A decision that arrives while an earlier advance() still holds the run lock is picked up by the next one; a test holds the lock with an asyncio.Event to prove it.
  • Behaviour is fixed per run. The effective limits and faults are snapshotted on the run (RunConfig), so a run resumed after a restart keeps the limits it started with.
  • Waiting is not working. The run's clock only runs inside advance() (_charge_active_time), so time waiting for a human never counts against MAX_RUN_SECONDS.

The cost is that every tick reads and writes the database, and anything not saved before advance() returns is gone. For a single process the in-memory approach would be simpler, but it loses the run on restart and ties the decision to the process that started the run. The re-entrant loop also makes testing direct: a test drives a run to the pause, makes a decision, and drives it again.

3.1 One tick (AgentLoop._tick)

1. re-read the run; stop if CANCELLED cancel between ticks 2. pending_tool_call? → _resolve_pending approved: stored args, key run_id:approval_id; rejected: ApprovalRejected observation 3. guardrails.check → max_steps | max_run_time P8 4. _call_llm: retry timeouts and retryable errors P5, backoff with jitter 5. step_count += 1; parser.parse(response) EmptyResponse → repair message; consecutive_malformed += 1 FinalAnswer → store answer; finish(final_answer) ToolCallAction → store assistant message; answer extra calls "not executed"; _dispatch(first call): parse JSON → registry.get → input_model validation repeat limit → previously rejected? → requires approval? yes → pause_for_approval → WAITING_APPROVAL (return) no → executor.run → observation + tool_calls row 6. consecutive_malformed > 2 or consecutive_tool_errors ≥ 3 → FAILED 7. charge active time; save (refused if the run was cancelled meanwhile)

5.2 Retry only what is worth retrying, at one layer (P5)

A retry helps only when the failure is temporary. The error taxonomy makes that a property of the error class: timeouts and transient errors are retryable; bad arguments, unknown tools, permanent errors and invalid tool output are not, because the same call would fail the same way. Each kind of call is retried in exactly one place: tool calls in ToolExecutor.run, LLM calls in AgentLoop._call_llm. The OpenAI SDK client is created with max_retries=0, because stacked retry layers multiply attempts (three layers of three attempts is 27 calls) and hide latency [R6].

Delays use capped exponential backoff with full jitter: uniform(0, min(4 s, 0.5 s · 2^(attempt−1))). Jitter keeps many callers from retrying in lockstep against a service that is recovering [R6]. Sleeps go through the injected Clock, so tests assert the exact delays without waiting, and the random generator is seeded from MOCK_SEED. Every attempt's timeout is capped by the run's remaining active time, and LLM retries stop when the backoff has used up the run's time budget (max_run_time).

5.3 Errors are context (P7)

A failed tool call is information the model can act on. An unknown service returns an error listing the known services; a schema violation names the fields; a timeout says it happened and that it was retryable. These reach the model as {"ok": false, "error": {...}} observations and the run continues. Only failures the model cannot fix end a run: the LLM is unavailable or rejects the request, a limit is hit, or the harness itself fails. Each ends with a recorded termination reason and a run_finished event. The consecutive-error limits stop the case where the model keeps producing failures instead of recovering.

5.4 Side-effecting retries are idempotent (P6)

Retrying create_incident after a timeout is only safe if a repeat cannot create a second incident: the timeout may happen after the incident was committed (the timeout_after_commit fault reproduces this). The harness passes an idempotency key, {run_id}:{approval_id}, set only in _resolve_pending and absent from every tool schema, so the model can neither see nor supply it [R7]. The incident store has a unique constraint on the key. The tool looks the key up first and returns the stored incident with deduplicated=true; if two calls race past the lookup, the loser hits the constraint, re-reads, and returns the winner's incident. The integration test sees two attempts and one incident.

6.2 Safety is enforced in code, not in the prompt (P3)

A system prompt can ask the model to wait for approval; it cannot make it. The approval gate is therefore in dispatch: a call to a tool with requires_approval is never executed from dispatch. The run is paused on an approval, and the tool's handler is reached only through _resolve_pending, after a stored decision. A decision is one conditional update that requires the approval to be pending and its run to be waiting, so a second decision gets 409 approval_not_pending and a decision after a cancel gets 409 run_not_waiting. As a second line of defence, the tool refuses to run without the harness-generated idempotency key, which only the approved path provides.

A human's rejection is enforced the same way. If the model proposes the exact call again (same tool and canonical arguments, compared by args_hash), dispatch answers it with the earlier rejection instead of asking the human a second time.

6.3 Approve exactly what executes (P4)

An approval covers one concrete action, not a tool. The approval row stores the validated, canonical arguments and the tool call id. On approval the harness executes those stored arguments, validated again, instead of asking the model to repeat the call, which could produce arguments the human never saw. A changed call, such as a SEV2 incident proposed after a SEV1 was rejected, is a different action and waits for its own approval.

6.4 Tool output is untrusted data (P9)

Knowledge-base documents and vendor notes can contain text written to steer the model. The harness wraps every observation in a JSON envelope, caps it at 4000 characters, and the system prompt says that tool output is data, never instructions. This lowers the chance that injected text is followed; it does not prevent it. The fixture vendor-note-untrusted.md contains an injection line, and the test scripts a model that obeys it: the injected create_incident call pauses at the gate, and no incident exists unless a human approves. The real defence is that the harmful consequence needs a human.

6.5 Bounded execution (P8)

Every run is bounded: 12 steps, 120 s of active time, 3 identical calls, 3 consecutive tool errors, 2 consecutive malformed replies, and a timeout on every attempt. Active time excludes the wait for approval. The API has no authentication, so a caller may lower these limits for its own run but never raise the operator's values (422 invalid_config_overrides); the env values themselves are capped at 50 steps and 600 s.

10. Comparison with existing runtimes

The harness solves the same problems as two general-purpose runtimes, the OpenAI Agents SDK [R2][R3] and LangGraph [R4], in a narrower way. The table compares only what the cited pages state.

The shared idea is that pausing for a human must survive the request that started the run: the Agents SDK serialises a run state, LangGraph saves a checkpoint, and this harness persists the run itself. Two differences are deliberate. First, the harness binds an approval to one call and executes the stored arguments; the Agents SDK page describes approving tool calls but does not say which arguments run after approval, and it offers “always approve” for a tool for the rest of a run, which this harness does not. Second, the harness runs one tool call per step, where the Agents SDK starts all function calls from a turn; one call per step keeps a single pause point and a single pending call per run. LangGraph's rule that an interrupted node restarts from its beginning means code before interrupt() runs twice, which is the same reason this harness makes its only side effect idempotent (P6).

Using either runtime would have been reasonable in production. For this exercise the loop is the thing being evaluated (P1), and a hand-written loop keeps every decision point visible in one file. A router such as LiteLLM [R9] would fit behind the LLMClient interface for multi-provider routing and fallbacks; its own retries would have to be disabled to keep one LLM retry layer (P5).

11. Testing strategy

Tests never call a real LLM or the network. ScriptedLLM replays responses, exceptions and callables; FakeClock makes backoff and active-time checks instant and exact; tool timeouts use real time with ≤ 50 ms values. Suites: 187 unit, 41 integration (loop + SQLite + ScriptedLLM), 26 API (httpx over the ASGI app), 5 optional live (skipped without LLM_API_KEY). 13. Limitations

The limitations below are deliberate scope decisions (PLAN §2) unless stated otherwise.

  • Single process. The per-run locks (RunService._locks) and the lock that allocates message and event sequence numbers (Repository._append_lock) live in one process, and the store is SQLite. Running two API processes against one database would allow two advance() calls on the same run.
  • A tick is not atomic across a crash. Each repository write is its own transaction. A crash in the middle of a tick can leave, for example, a tool message without the matching run update. There is no resume-after-crash: a run left RUNNING by a crash stays so. A clean shutdown is handled: in-flight runs are marked FAILED/internal_error with message “shutdown”.
  • No approval expiry. A pending approval waits forever.
  • No approver authentication or roles. decided_by is free text and the API has no authentication. This is also why per-run overrides may only lower limits.
  • Cancellation is cooperative. A cancel takes effect at the next tick or at the loop's next save. A tool call already in flight finishes and is recorded, so an already-approved create_incident completes if the cancel lands while it is executing, and its events can appear after the cancel's run_finished.
  • One tool call per step. Extra calls in one reply are answered “not executed”; independent read-only calls are not run in parallel, which costs steps.
  • Lock bookkeeping. RunService keeps one lock entry per run for the life of the process.
  • Final answers are not checked against the trace. The live run produced an answer claiming an incident had been opened when none was (§8.2). The harness records what actually happened, but it does not stop a model from stating otherwise.
  • Basic prompt-injection defence. JSON wrapping, truncation and a system-prompt rule. There is no classifier or content filtering; the approval gate limits the consequence of an injection, not the injection itself.
  • Also out of scope: token and cost budgets, semantic knowledge-base search, database migrations, OpenTelemetry export. The scripted provider replays one scenario for every objective.

14. Future improvements

  • Crash safety: lease-based ownership of running runs (heartbeat + reclaim), and one transaction per tick (outbox for events) so a tick commits or not at all.
  • Horizontal scale: Postgres with row locks (SELECT … FOR UPDATE SKIP LOCKED) instead of in-process locks; a queue for background advances.
  • Approvals: TTL with automatic rejection, approver authentication and roles, notification hooks.
  • Answer grounding: check a final answer against the run's tool calls before accepting it (e.g. an incident id must come from a succeeded create_incident), and send a repair message otherwise.
  • Budgets: token and cost limits per run using the usage already recorded on llm_response events.
  • Tools: parallel execution of read-only calls; semantic KB search; per-tool rate limits and circuit breakers.
  • LLM: multi-provider routing and fallbacks (e.g. LiteLLM [R9]) behind LLMClient.
  • Observability: OpenTelemetry export of the same events as spans.
  • Operations: Alembic migrations; lock cleanup when runs finish.
